<objective>
Build the outbound half of Vapi assistant configuration: render an assistant's system
prompt, function (tool) schemas, and per-tool spoken messages from an org's entry
orchestrator and its granted workflows, then PATCH that configuration onto the org's
mapped Vapi assistant.

Purpose: 139-CONTEXT.md names this the largest gap — `src/lib/vapi/sync-assistants.ts` only
mirrors Vapi's assistants INTO `assistant_mappings`; nothing in the codebase writes a
prompt or a tool schema TO Vapi. Every change made to the Cuts & Culture assistant (the v3
prompt, the eight `request-start` lines, the delay/failure lines — see
`.planning/workstreams/omnichannel-agent-orchestration/canary/vapi-tool-messages.md`) was a
manual PATCH from an uncommitted probe script. This is the mechanism that makes voice
provisionable instead of hand-configured, and the same mechanism that will carry Phase
138's `customerAddress` parameter into the Vapi schema once that phase adds it — this plan
does not implement modality (138 is not built yet; do not reference
`organizations.service_location_mode`, it does not exist), but the function schema
renderer must derive parameters from each workflow's own `input_schema` generically, so a
future field there reaches Vapi automatically with no change to this code.

Output: a pure renderer (fully unit-tested, no network) plus a thin PATCH wrapper. The live
PATCH itself is proven only by a `tests/manual/*` probe (this repo's existing convention for
anything that touches a real external account — see `tests/manual/vapi-set-tool-messages.test.ts`)
excluded from the default test run, never executed by this plan.
</objective>

```ts
export interface AssistantConfigWorkflow {
  toolName: string
  description: string
  inputSchema: InputSchemaMap  // from @/lib/workflows/derive-input-schema
}
export interface AssistantConfigSource {
  systemPrompt: string
  workflows: AssistantConfigWorkflow[]
}
export interface RenderedVapiFunction {
  name: string
  description: string
  parameters: { type: 'object'; properties: Record<string, unknown>; required: string[] }
}
export interface RenderedToolMessage {
  toolName: string
  requestStart: string
}
export interface RenderedAssistantConfig {
  systemPrompt: string
  functions: RenderedVapiFunction[]
  toolMessages: RenderedToolMessage[]
}

export function renderAssistantConfig(source: AssistantConfigSource): RenderedAssistantConfig
```

`inputSchemaFieldToJsonSchema(field: InputSchemaField): unknown` maps `type` ('string' |
'number' | 'integer' | 'boolean' | 'array' | 'object', default 'string') to
`{type, description}` (include `description` only if present; include `enum` only if
present). This is a small, self-contained mapping — do not import Zod for it.

`requestStart` default: a short, generic, domain-neutral line such as `"One moment."` for
every tool — this module has no way to know which tools are slow for an org it has never
measured, and per CLAUDE.md's product framing this is reusable platform code, not a place
to bake in Cuts & Culture's specific measured wording. Note in a comment that per-tool
tuning (like the phrasing and delayed/failed messages recorded in
`vapi-tool-messages.md`) is an operator refinement layered on top later, out of this
renderer's scope.

Create `src/lib/vapi/sync-assistant-config.ts`:
```ts
export interface PushAssistantConfigResult { ok: boolean; error?: string }
export async function pushAssistantConfig(
  supabase: SupabaseClient<Database>,  // RLS-scoped, same convention as syncVapiAssistants
  organizationId: string,
  vapiAssistantId: string,
): Promise<PushAssistantConfigResult>
```
Sequence:
1. Resolve the org's entry orchestrator: the agent pointed at by
   `agent_channel_defaults` for channel `'voice'` (fall back to `'web_widget'`'s default if
   voice has none configured — an org may run the mesh on the widget before voice is wired).
   No orchestrator configured -> `{ok: false, error: '...'}`, no PATCH attempted.
2. Resolve that agent's rendered system prompt the same way `resolveAgent()` does — via
   `active_prompt_version_id` -> `agent_prompt_versions.system_prompt`. Never fall back to
   `agents.system_prompt` (that column is legacy/unused by the runtime — see 139-01's
   context note on this).
3. Resolve the workflows this agent's mesh can reach: this agent's own `agent_tools`
   (workflow-sourced) UNION every workflow granted across its outgoing `agent_partners` +
   `agent_partner_workflow_grants` edges — Vapi needs every function the CALL might invoke
   through delegation, not only the orchestrator's own direct grants (which, per this
   phase's own verified graph, is normally empty for an orchestrator).
4. Call `renderAssistantConfig({systemPrompt, workflows})`.
5. PATCH `/assistant/:vapiAssistantId` with the resolved shape from Task 1's discovery step.
6. Never throw past this function's boundary — return `{ok: false, error}` on any Vapi
   error, same never-throw convention as `syncVapiAssistants()`.

Write `tests/manual/vapi-push-assistant-config.test.ts` (excluded from the default Vitest
