<objective>
Build the pure rendering mechanism that turns a prompt template containing
`{{business_name}}` / `{{business_location}}` tokens into concrete text for one target
organization, plus the fact-resolver that supplies those values. This is what makes "a
template carries behaviour; a tenant supplies its facts" (139-CONTEXT.md, Locked decisions)
real instead of aspirational.

Purpose: both the install path (a later plan, renders once at install time and persists the
result into a fresh `agent_prompt_versions` row) and the one-off content fix that removes
Cuts & Culture's hardcoded facts from its own live prompts (a later, sibling plan) need the
exact same renderer — building it once here means neither reimplements token substitution.

Output: `src/lib/org-templates/prompt-template.ts`, fully unit-tested, with no dependency on
`org-templates/snapshot.ts` or `install.ts` (a pure module deliberately kept independent so
it can land in the same wave as those files without file contention).

Create `src/lib/org-templates/prompt-template.ts`:

```ts
export interface TenantFacts {
  businessName: string
  businessAddress: string | null
}
```

`renderPromptTemplate(template: string, facts: TenantFacts): string` — plain, dependency-free
string substitution (no templating library needed for two tokens):
- `{{business_location}}` -> `${facts.businessName}, ${facts.businessAddress}` when
  `businessAddress` is non-null/non-empty, else just `facts.businessName`.
- `{{business_name}}` -> `facts.businessName`.
Use `.replaceAll()`; order does not matter since the two token literals never overlap and
`facts.businessName` is real-world text that will not itself contain a `{{...}}` token.

`resolveTenantFacts(admin: SupabaseClient<Database>, orgId: string): Promise<TenantFacts>`:
1. Read the `organizations` row for `orgId` (name + the six address columns above). This is
   the baseline — always available, even for an org created seconds ago with no integration
   connected yet.
2. Try `getXkeduleCredentialsForOrg(orgId, admin)`. If credentials resolve, call
   `xkeduleFetchJson<{businessName?: string|null; address?: string|null}>('/api/v1/business-info', 'GET', null, credentials)`
   inside a try/catch. On success, prefer its non-empty `businessName`/`address` over the
   organizations-row values.
3. Never throw. Any failure at step 2 (no integration, decrypt error, fetch error, timeout)
   falls back to step 1's values without propagating the error — this function is called
   from the install path, where a missing integration is the NORMAL case for a fresh org
   from a template, not an error condition.
4. Assemble the organizations-row fallback address as
   `[address_line1, address_line2, [address_city, address_state].filter(Boolean).join(', '), address_postal_code].filter(Boolean).join(', ')`,
   or `null` if every part is empty.

Document at the top of the file, explicitly, that this module carries NO tenant-specific
string anywhere (no "Cuts & Culture", no "Newbury Street") — it is reusable platform code,
and the six live prompts that currently hardcode those facts are fixed by a separate,
tenant-scoped script, not by this module.
