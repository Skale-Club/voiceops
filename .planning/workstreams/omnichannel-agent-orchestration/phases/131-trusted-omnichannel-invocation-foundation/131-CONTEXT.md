# Phase 131: Trusted Omnichannel Invocation Foundation - Context

**Gathered:** 2026-09-03
**Status:** Ready for planning
**Source:** Operator architecture discussion and repository analysis

<domain>
## Phase Boundary

Establish the trusted, typed boundary through which voice and text can invoke the existing Xphere agent runtime. Add the schema and resolution primitives needed to bind a Vapi assistant to an internal entry agent and make `voice` a first-class channel. Restore a trustworthy Vapi/Action Engine regression baseline.

This phase does not cut production Vapi traffic over to specialist execution, redesign delegation authorization, implement Xkedule mutation idempotency, build observability UI, or configure the Cuts & Culture specialist graph. Those belong to Phases 132-136.

</domain>

<decisions>
## Implementation Decisions

### Runtime ownership
- Vapi continues to own telephony, STT, TTS, and the live conversation loop.
- Xphere owns tenant resolution, internal agent invocation, workflows, and provider actions.
- The Action Engine remains the only authoritative provider execution path.
- Phase 131 introduces an internal invocation gateway around `runAgent`; it does not replace `runAgent` or create a second agent runtime.

### Shared invocation contract
- Define a typed envelope containing server-resolved `orgId`, `agentId`, `channel`, external interaction ID, optional conversation/call ID, actor/contact identity, locale, user message or explicit intent, correlation/trace ID, and stable ingress idempotency key.
- Organization and agent identity are trusted internal fields. Provider payload arguments and LLM-generated tool arguments cannot override them.
- The gateway supports blocking and streaming callers without changing existing widget SSE behavior.
- The same agent ID can be invoked from `web_widget` and `voice`; channel differences use existing channel overrides and runtime budgets.

### Voice channel
- Add `voice` additively to the Postgres `agent_channel` enum and the TypeScript/UI channel registries.
- Voice policies can override prompt suffix, model, temperature, max tokens, and max history through the existing `channel_overrides` mechanism.
- Voice-specific delegation and latency enforcement is defined by the invocation contract now and implemented in the routing/safety phases.

### Vapi binding and trust
- Add an optional `entry_agent_id` foreign key to `assistant_mappings`; null preserves the legacy direct-workflow behavior.
- The binding must reference an agent from the same organization. Enforce this through a composite database constraint or a server-side invariant backed by tests; prefer the database constraint if compatible with the existing schema.
- Resolve the organization from trusted Vapi assistant/call/number mappings first, then resolve `entry_agent_id` from that organization-scoped mapping.
- Never accept `organization_id`, `orgId`, `agent_id`, or `agentId` from Vapi tool arguments as routing authority.
- Existing mappings remain valid and no automatic backfill binds production assistants during this phase.

### Compatibility and rollout
- No production route cutover occurs in Phase 131. Existing `/api/vapi/tools` behavior remains the default.
- Database changes are additive and live in a new numbered migration; migration history is never rewritten.
- Authenticated configuration reads/writes continue through RLS. Vapi webhook resolution uses the established service-role/bootstrap pattern with explicit tenant checks.
- Repair the stale `.maybeSingle()` Vapi test mocks and isolate Action Engine unit tests from live Redis availability before adding new behavior assertions.

### the agent's Discretion
- Exact file split and function names for the invocation gateway, provided there is one public typed entry point and no duplicate runtime.
- Whether correlation and idempotency identifiers are generated by a pure helper or inside the gateway.
- Exact composite-key database implementation used to prove that assistant mapping and entry agent belong to the same organization.
- Whether the assistant-mapping dashboard exposes `entry_agent_id` during this phase or a later rollback/configuration phase. No new UI is required to satisfy Phase 131.

</decisions>

<specifics>
## Specific Ideas

- A direct Vapi function-to-specialist optimization is required by the milestone, but its routing logic belongs to Phase 132; Phase 131 only provides the trusted agent binding and gateway contract.
- A voice request should be constructible in tests without making an external Vapi or OpenRouter call.
- The gateway must preserve trace and idempotency identifiers supplied by trusted channel adapters and generate them when absent.
- Existing assistant mappings with `entry_agent_id = NULL` must remain on the legacy behavior without configuration changes.

</specifics>
