  <name>Task 6: Accept the nested tool-call shape Vapi actually sends</name>
  <files>src/types/vapi.ts, src/app/api/vapi/tools/route.ts, tests/action-engine.test.ts, tests/manual/prod-shape-probe.test.ts, tests/manual/vapi-call-log.test.ts, tests/manual/vapi-secret-fp.test.ts, .planning/workstreams/omnichannel-agent-orchestration/FINDINGS-OUTSIDE-SCOPE.md</files>
  <action>
  The first real tool call ever to reach production (call `01a06de4-7c3f-7000-89bc-4f8adb241ff7`)
  carried every `toolCallList` item as `{id, type:'function', function:{name,
  arguments:"json-string"}}`. The schema only accepted the flattened
  `{id, name, arguments:object}` shape, so `safeParse` failed and the route answered
  `{results: []}` before logging anything — zero rows in `workflow_runs`, which is what
  made it look like nothing had happened. Proven, not inferred, by probing production with
  the assistant's own secret in both shapes: the flat shape returned real data, the nested
  one returned empty, and a wrong-secret control also returned empty — so the secret was
  not the cause. Made the schema a union of both shapes; `normalizeVapiToolCall()` folds
  either into the flat `VapiToolCall` the route, logging, and idempotency code already use,
  decoding string-encoded arguments. Also recorded, as an out-of-scope finding, that the
  webhook secret configured in the Vapi assistant fingerprints as Coolify's *preview*-scope
  value, and production currently accepts it — not the cause of this defect, but a latent
  risk if a future deploy or env sync moves the container onto the production-scope value.
  </action>

tested against a mock. The voice prompt leads the call, looks the caller up before
speaking, discovers the service from the caller's own words, gates booking on price

surface for the mesh.
