<objective>
Give the booking engine the one thing it is missing to serve both a shop the customer
visits and a business that visits the customer: a per-organization setting, a schema
contract for the address field, and a single rendering function for the instruction text —
so no later plan, and no future tenant's prompt author, has to hardcode "ask" or "never
ask" again.

This plan produces contracts only (a migration, a schema map, two pure functions, one
fail-closed resolver). Nothing here is wired into the live runtime yet — Plan 138-02 does
that. Voice/Vapi is out of scope for the whole phase: nothing writes a schema or a prompt
into a Vapi assistant today (verified — `src/lib/vapi/sync-assistants.ts` is inbound-only),
building that outbound sync is Phase 139's job, and this plan does not pretend otherwise.
</objective>

    - `applyServiceLocationMode(inputSchema, mode, fieldKey = 'customerAddress')` — a pure
      function operating on the `InputSchemaMap` type from
      `src/lib/workflows/derive-input-schema.ts` (re-export/import that type; do not
      redefine it):
      - `mode: 'on_premises'` deletes `customerAddress` from the returned map entirely (the
        model must not even see the field can exist).
      - `mode: 'at_customer'` keeps the field and sets `required: true`.
      - `mode: 'either'` keeps the field and sets `required: false`.
      - Any value other than the three above (including `undefined`, `null`, an empty
        string, or a typo) behaves exactly like `'on_premises'` — fail closed, never
        fail open into asking for an address.
      - A map that has no `customerAddress` key is returned unchanged for every mode (a
        workflow that isn't `book_appointment` is never touched).
    - `renderServiceLocationBlock(mode)` — a pure function returning one string per mode,
      to be the single place this wording is authored (see 138-CONTEXT.md "Where the
      decision lives" — no prompt file may hardcode this text again):
      - `'on_premises'`: states plainly that this business does not travel and the address
        must never be asked for or recorded.
      - `'at_customer'`: states that the address must be collected, read back, and
        confirmed after the price is accepted and before availability is checked (per
        138-CONTEXT.md "When the address is collected" — where the customer is constrains
        when they can be served).
      - `'either'`: states that exactly one narrowing question decides which of the above
        applies (per 138-CONTEXT.md: "Is this at the shop, or are we coming to you?"),
        asked at the same point — after price acceptance, before availability.
      - Any unrecognised mode renders the same text as `'on_premises'` (fail closed).
      - Assert the three real strings are non-empty, distinct from each other, and that
        none of the three ever appears verbatim inside another mode's output (so a
        find-and-replace of one can't silently corrupt another).
    - `resolveServiceLocationMode(organizationId)` — modeled on
      `src/lib/agent-runtime/routing-mode.ts`'s `resolveChannelRoutingMode()`: creates its
      own client via `createServiceRoleClient()` from `@/lib/supabase/admin` (mock that
      module exactly as `tests/channel-routing-mode.test.ts` does), selects
      `service_location_mode` from `organizations` for the given id, and fails closed to
      `'on_premises'` on a query error, a missing row, a null value, or any string outside
      the three recognised modes. Never throws.
  </behavior>
